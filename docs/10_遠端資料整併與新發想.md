## 2. 遠端 repo 有哪些東西（相較於本地預研究）

遠端是一個**資料管線 repo**，有幾個特點：

- 規範嚴謹：每份資料都有 `metadata` 與 `limitations`，並由不同 Agent 獨立巡檢，結果放在 `data/quality/`。
- 有 GitHub Actions 每日更新。
- 腳本依來源分開：`update_data`、`update_bus_feeds`、`update_metro`、`update_population`、`update_pto_extended`、`update_urban`、`update_background`。

| 類別 | 遠端整理好的資料 | 本地預研究的狀態 → 整併後的變化 |
|---|---|---|
| 公車 feeds | `data/taipei_feeds/` 15 份，含 **`occupancy_events`（BusSeatEvent，車上人數）**、`special_schedules`、`vehicles`（電動、低地板） | 本地只有原始 blob，而且**誤判擁擠度資料已停滯** → 已更正（08 A10） |
| ID 語意 | 明確區分 `route_id`（主路線）、`subroute_id`（附屬路線）、`depot_id`（車輛所屬場站）；並標註 `GoBack=2/3` 不是方向 | 本地的 `prelim_overlap.py` 把 GetStop 的 `goBack` 當成方向，也沒有區分支線 → **要依遠端的語意修正** |
| 路線年運量 | `pto_extended/route_annual.json`（2025 年，363 條路線） | 本地原本卡在 OCR → **已解決**，mock 已用它校準 |
| 業者月報、公車專用道月運量 | `operator_monthly`、`bus_lane_monthly` | 新資料：專用道各路廊的月運量 |
| **評鑑** | `assessment_operator_scores`、`assessment_punctuality`（各路線準點率）、**`assessment_station_checks`（各場站的休憩室與盥洗室分數）** | 加分項 D2 有了部分資料 |
| 捷運 | `metro/station_hourly_flows.json`（日期 × 小時 × 站的進站、出站，2025-10 至 2026-09）、`exit_bus_connections.json`（6,931 筆捷運出口與公車的對應） | 本地只有出入口座標 |

## 3. 新發想（依價值排序）

0. ⭐（新增）**拿既有的預約公車驗證冷區模型**：臺北 12 條路線的預約班次，就是主管機關已經認定的低需求時段。拿來當作冷區判斷的驗證標籤，再找出還沒有設預約班次的冷區。

1. ⭐ **`BusSeatEvent` → 有方向、分時的實際載客量**：唯一不用申請的公開實際載客訊號。持續收集後可以畫出路段載客流量圖、淨上下車熱圖、載客剖面。詳見 [11](11_時間地點方向需求熱圖設計.md)。
2. ⭐ **「潛在需求 − 實際載客」落差圖**：最小統計區人口（加上信令的日夜比例）對照公車實際載客，找出「有人但沒有服務到」的區塊。這比單純看冷區更適合用來決定 DRTS 的位置。
3. **準點率 × 重疊度**：準點率差、又和捷運高度重疊的路線（`assessment_punctuality`）是優先檢討的對象。重疊路段在塞車時，班次常常一起延誤、串成一列。
4. **潮汐方向 → 區間車與駕駛休息**：單向空車的回程可以考慮改成區間車，省下的車次與駕駛時間可以拿去補休息或補其他路線（缺工是硬限制）。
5. **場站查核分數 × 公廁 5 分鐘步行圈 × 大型車格位**：做成「折返點休息設施評分」。場站名稱要先地理編碼；只能使用來源有核實的對應。
6. **大車限制路段 × 窄巷 × 冷區** → 小型巴士的優先區。
7. **YouBike 往捷運站集中的 OD** → 接駁缺口。補足公車資料看不到的第一哩、最後一哩需求。
8. **公車專用道路廊月運量**：檢驗幹線公車的成效，並和平行的捷運路段比較。
