# 07 Mock 資料規格

## 1. 為什麼需要 mock

- 逐站分時的上下車資料存在 TDX 票證服務中，但需要經過審核，而且每次申請 500 點（見 [01](01_資料來源目錄.md) A4）。
- 在拿到真實資料之前，MVP 的分析與視覺化管線要先用 mock 資料開發。
- 原則：
  1. **路網、站位、班距都用真實資料**，只有運量是合成的。
  2. 所有 mock 檔案的檔名都加 `mock_` 前綴，並且有 `is_mock=1` 欄位。
  3. 欄位結構盡量接近 TDX 票證資料。TDX 的實際欄位要登入後才看得到，**目前是推測**，拿到真實資料後再寫轉換器對齊。

## 2. 產生方式

```bash
uv run --no-project --with numpy python -I scripts/gen_mock_ridership.py . --seed 42
```

- 先決條件：`raw_data/taipei_feeds/*.gz`（遠端管線）、`raw_data/research/mrt_exits.csv`、`data/pto_extended/route_annual.json`。
- 輸出到 `raw_data/research/mock/`（gitignore，可以重新產生）。依 AGENTS.md，`data/` 只放整理過的官方資料，所以 mock **不放在** `data/`。
- 預設會用 `data/pto_extended/route_annual.json` 校準；傳入 `--calib ""` 可以關閉校準。
- 2026-10-21 實測：784,470 筆路線站點時段紀錄、5,372 個站位，約 11 秒完成。

## 3. 輸出欄位

### 3.1 `mock_stop_hourly.csv`（路線 × 方向 × 站序 × 日型 × 小時）

| 欄位 | 型別 | 說明 |
|---|---|---|
| day_type | str | `weekday` 或 `holiday` |
| hour | int | 5–23 |
| route_id | int | 公運處 GetRoute.Id |
| route_name | str | 路線名稱 |
| go_back | str | 0 = 去程，1 = 返程（另有少數其他代碼） |
| seq_no | int | 站序 |
| stop_location_id | int | 站位 ID（對應 GetStopLocation.id） |
| stop_name | str | 站名 |
| lon, lat | float | WGS84 |
| boardings | int | **mock** 上車人次 |
| alightings | int | **mock** 下車人次 |
| trips | int | 該小時通過的班次數（由尖峰、離峰班距推算） |
| is_mock | int | 一律為 1 |

### 3.2 `mock_stoplocation_hourly.csv`（站位 × 日型 × 小時）

欄位：`day_type, hour, stop_location_id, stop_name, lon, lat, dist_mrt_m, boardings, alightings, trips, pax_per_trip, is_mock`

- `pax_per_trip` =（上車 + 下車）÷ 通過的班次數，是**單一站位**的值。
- 法規的「每班次低於 5 人上下車」是以**路段**為單位，需要把路段內各站加總後再比較。

## 4. 生成模型（假設都寫在程式碼裡，可以調整）

### 4.1 站位吸引力（不隨時間變動）

```
w = LogNormal(0, 0.6)                         # 個別站位的隨機差異
  × (1 + 2.0·exp(−d_MRT / 300 m))             # 靠近捷運的轉乘吸引
  × (1 + 0.35·ln(1 + 停靠路線數))              # 公車走廊
  × (0.4 + 0.6·exp(−d_臺北車站 / 8 km))        # 離市中心越遠越低
```

### 4.2 路線方向的日運量

- 每個路線方向先抽一個 `LogNormal(ln 1800, 0.8) × (1 + 0.04·站數)`。
- 再整體縮放，讓**平日全路網上車總量 = 1,141,764**（2024 年臺北市公車日均運量，見 03）。
- 假日運量乘以 0.65。

### 4.3 時段分布

- 平日是雙峰：07–09 時、17–19 時。
- 假日是午間的平緩高原。
- 數值見程式中的 `PROFILE`。

### 4.4 上車與下車

- **上車比例** ∝ w ×（1 − 0.85 × 站序位置），愈接近終點上車愈少，末站為 0。
- **下車**：在第 i 站上車的人，下車站 j > i 的機率 ∝ w_j × exp(−(j−i−5)² / 50)，偏好 5 站左右後下車。這樣**每條路線方向的上下車總量守恆**，也就能算出車上載客量的變化曲線。
- 最後加上 Poisson 雜訊。

### 4.5 班次數

- 尖峰用 `peakHeadway`，離峰用 `offPeakHeadway`。格式 `"0715"` 取平均 11 分。
- 沒有填的路線：尖峰預設 12 分，離峰預設 max(1.5 × 尖峰, 15) 分。

## 5. 已知限制（使用 mock 時必須注意）

1. **路線之間的運量分配**：加上 `--calib <route_annual.json>` 後，有 332/416 條路線（以名稱完全比對）改用 **2025 年真實年運量**。換算方式：真實年運量 ÷（250 + 115 × 0.65）個平日等效日 ÷ 方向數，得到每個方向的平日運量。其餘 84 條比對不到的路線（例如名稱寫法不同、新北路線）維持隨機抽樣，再縮放到已校準路線的中位數。輸出中的 `route_total_calibrated` 欄位標示每條路線是否已校準。
   - 實測（2026-10-22）：平日上車合計 1,350,427 人次，共 701,359 筆紀錄、5,355 個站位。
   - 指令：`uv run --no-project --with numpy python -I scripts/gen_mock_ridership.py .`（預設就會校準）
   - 名稱比對不到的路線，**需要建立別名對照表**（待辦 B2）。
2. 總量 114 萬人次包含聯營路線在新北境內的路段，口徑並不精確。
3. 沒有轉乘、沒有 OD 鏈；`P` 矩陣只是用來保持上下車守恆的簡化。
4. 只用了 `peakHeadway` 與 `offPeakHeadway`，沒有用 GetTimeTable 的實際發車時刻。
5. 沒有考慮地形、土地使用與人口，所以 mock 的「冷區」主要反映「離捷運遠、離市中心遠、停靠路線少」三個條件。**以 mock 找出的冷區有一部分只是重現上面的假設，不能當作發現。**
6. 初步檢查（平日）：單一站位的「每班次上下車人數」中位數，08 時 1.0、14 時 0.9、22 時 0.75；08 時上車最多的前幾名是捷運公館站、捷運劍潭站、明湖國小、臺北車站。這只代表模型的行為合理，**不代表真實情況**。

## 6. 替換成真實資料的步驟

1. 申請 TDX「臺北市市區公車分時上下車人次資料」，取得樣本後記錄實際欄位。
2. 寫 `adapters/tdx_ticket_to_stop_hourly.py`，把真實資料轉成 3.1 的格式。
3. 用新北與公路局的資料補齊聯營路線。
4. 依真實資料重新校正 4.1 的參數。之後在沒有真實資料的期間，可以用校正後的 mock 做情境模擬。

## 7. 其他可能需要的 mock

| Mock | 用途 | 狀態 |
|---|---|---|
| 公車 OD（站到站） | 旅次重疊度 | 未做；可以從 4.4 的 P 矩陣延伸 |
| 端點站設施（有沒有廁所或休息室、可停幾輛大車） | 駕駛休息評分 | 未做；建議**實地或向公運處調查**，不要用 mock |
| DRTS 預約需求 | DRTS 模擬 | 未做；可以依 TDX v3 DRTS 資料標準設計 |
| 駕駛班表 | 過勞檢核 | 未做；可以用車輛班次（block）近似 |
